# 问题 #9：WaitAll 提前消耗部分已就绪对象并可能二次消耗

## 1. 问题编号

`9`

## 2. 问题位置

- 文件路径：`src/ke/wait.zig`
- 函数/模块：`keWaitForMultipleObjectsWaitAll()`
- 行号或代码片段：原实现在遍历对象时对每个已就绪对象立即调用 `tryConsumeWaitable()`；若发现某个对象未就绪，前面已被消费的状态不会恢复。

## 3. 问题描述

`WaitAll` 语义要求只有当所有对象同时满足时才一次性消耗。原实现会在检查过程中消费部分对象，随后因为其他对象未就绪继续等待；这些对象已经失去许可或触发自动复位。当全部对象最终就绪时，实现又对所有对象再次调用 `tryConsumeWaitable()`，造成重复消耗。

## 4. 复现路径

构造多个信号量或自动复位事件，使第一个对象可满足而第二个对象未满足。线程进入 `WaitAll` 后，第一个对象会被提前消耗；后续即使第二个对象就绪，第一个对象可能无法再次满足。若两者最终都满足，最后一次遍历还会再次消耗全部对象。

## 5. 影响范围

- 导致多对象等待返回结果错误或永久等待。
- 造成信号量许可丢失、自动复位事件状态错误。
- 影响依赖 `KeWaitForMultipleObjects` 全等待语义的驱动和内核同步路径。

## 6. 严重程度

- High

## 7. 可能原因

实现把 `WaitAny` 的“遇到第一个可消费对象即返回”模式误扩展到 `WaitAll`，在逐项检查时执行了消费操作。

## 8. 权威参考依据

- 项目源码：`src/ke/wait.zig` 中 `tryConsumeWaitable()`、`isWaitableReady()` 与多对象等待路径。
- Windows 多对象等待的公开语义应依据 Windows 7 文档或 ReactOS 行为进一步对照；本报告未引用 REA 二进制结论。
- `/home/mobtgzhang/api.json` 是 REA 接入配置，不是等待 API 文档。

## 9. 建议修复方案

先只使用 `isWaitableReady()` 判断全部对象是否满足；全部满足后，在同一个持锁临界区内对每个对象调用一次 `tryConsumeWaitable()`。未全部满足时不得消费任何对象。

## 10. 验证方法

- 运行 `zig build test` 与 `zig build -Darch=x86_64`。
- 构造两个信号量：先只释放第一个，确认其计数不会减少；再释放第二个后确认两个各消耗一次且等待返回。
- 后续可用 REA 对照 `ntoskrnl.exe` 中多对象等待导出函数的边界行为，但当前修复先恢复 WaitAll 的基本消耗一致性。

## 11. 状态

- Fixed

## 12. 修复说明

已移除提前消费和重复消费逻辑，`WaitAll` 现在先检查全部对象就绪，再统一消耗一次。宿主单元测试与 x86-64 构建通过。
