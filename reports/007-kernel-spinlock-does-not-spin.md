# 问题 #7：内核 SpinLock 不自旋且可被并发覆盖

## 1. 问题编号

`7`

## 2. 问题位置

- 文件路径：`src/ke/sync.zig`
- 函数/模块：`SpinLock.acquire()`、`SpinLock.release()`
- 行号或代码片段：原 `acquire()` 不检查已有持有者是否属于其他线程，直接保存中断状态并把 `locked` 置为 `true`。

## 3. 问题描述

`SpinLock.acquire()` 在锁已被其他线程持有时仍会立即成功。它会覆盖 `saved_if`、`owner_tid` 和 `recursion_count`，随后任一持有者释放都可能破坏另一个持有者的中断状态或提前解锁。该类型名称和注释均表明这是自旋锁，但原实现没有任何自旋或原子获取逻辑。

## 4. 复现路径

两个线程或中断上下文访问同一个 `SpinLock` 实例。若线程 A 先调用 `acquire()` 且尚未释放，线程 B 随后调用 `acquire()`，B 也会成功进入临界区。A 或 B 任一方先释放时，共享锁状态即被破坏。

## 5. 影响范围

- 导致临界区互斥失效、数据竞争和状态损坏。
- 可能恢复错误的 `saved_if`，造成中断被误开启或长时间关闭。
- 影响使用 `ke.sync.SpinLock` 的驱动队列、桌面组合器和用户态服务锁。

## 6. 严重程度

- Critical

## 7. 可能原因

实现只维护了锁状态字段，没有使用原子比较交换或自旋等待。`owner_tid` 检查只用于递归检测，但未先判断锁是否已由其他持有者占用。

## 8. 权威参考依据

- 项目源码：`src/ke/sync.zig` 的 `SpinLock` 与调用点。
- 项目源码：`src/arch.zig` 提供保存/恢复中断状态与 CPU relax 接口。
- 本问题由互斥语义和代码控制流审计确认；未引用 REA 对 Windows 7 镜像的二进制分析结论。
- `/home/mobtgzhang/api.json` 是 REA 接入配置，不作为本锁实现的行为依据。

## 9. 建议修复方案

为锁增加原子保护字，先在同线程递归场景保留 panic，再通过比较交换从 0 获取到 1；获取失败时执行 CPU relax 并重试。持锁后保存中断状态和所有者。释放时校验所有者，清零所有者与锁标志后用 release 语义释放保护字，最后恢复中断状态。

## 10. 验证方法

- 运行 `zig build test`，确认现有同步与内核桩审计测试通过。
- 运行 `zig build -Darch=x86_64`，确认内核构建通过。
- 后续可编写并发压力测试，令多个宿主线程竞争同一锁并检查临界区不重叠。
- 本修复不涉及 Windows 7 二进制可观察行为，不需要 REA 对照。

## 11. 状态

- Fixed

## 12. 修复说明

已增加 `lock_guard` 原子保护字，`acquire()` 现在会真正自旋并使用 acquire 语义获取锁；`release()` 在校验所有者后以 release 语义解锁，再恢复中断。`zig build test` 与 `zig build -Darch=x86_64` 均通过。
