# 问题 #8：Semaphore 的读改写序列存在丢失更新竞争

## 1. 问题编号

`8`

## 2. 问题位置

- 文件路径：`src/ke/sync.zig`
- 函数/模块：`Semaphore.acquire()`、`Semaphore.release()`
- 行号或代码片段：原实现先原子读取 `count`，再用 `@atomicRmw` 加/减 1，最后依据旧值判断是否回滚。

## 3. 问题描述

计数检查与修改之间没有比较交换原子性。多个线程同时获取或释放信号量时，可能出现计数越过 0 或上限后又用非原子 store 覆盖回错误值，导致计数错乱、许可丢失或超出 `max_count`。

## 4. 复现路径

两个或多个线程同时对同一 `Semaphore` 调用 `acquire()` 或 `release()`。当它们读取到相同旧值并交错执行原子读改写时，回滚路径会把其中一个线程的结果覆盖掉，最终计数不再等于成功操作的净差值。

## 5. 影响范围

- 影响内核同步对象和依赖信号量的临界区等待者唤醒。
- 可能造成获取许可失败但计数被错误减少，或释放许可失败但计数被错误增加。
- 连锁影响等待线程的唤醒数量和临界区并发度。

## 6. 严重程度

- High

## 7. 可能原因

单个 `@atomicRmw` 本身是原子的，但“读取判断、修改、再覆盖回滚”组合不是事务。需要以比较交换循环保证只有在观察到旧值仍然有效时才提交增减。

## 8. 权威参考依据

- 项目源码：`src/ke/sync.zig` 中 `Semaphore` 的计数实现。
- 本问题由并发语义审计确认；未引用 REA 对 Windows 7 镜像的二进制分析结论。
- Windows 7 信号量 API 的精确返回码仍需 Windows 文档或 REA 对照验证；本报告不声称该对照已完成。
- `/home/mobtgzhang/api.json` 是 REA 接入配置，不是 API 文档。

## 9. 建议修复方案

将 `acquire()` 和 `release()` 改为比较交换循环。获取路径仅在旧值大于 0 时提交 `old - 1`；释放路径仅在旧值小于 `max_count` 时提交 `old + 1`。比较交换失败后重新读取观察值并重试，不再使用非原子 store 回滚。

## 10. 验证方法

- 运行 `zig build test` 和 `zig build -Darch=x86_64`。
- 后续可增加多宿主线程压力测试，统计成功 acquire/release 次数并断言最终计数一致。
- 后续如需对齐 Windows 7 内核信号量可观察行为，可用 REA 对照 `ntoskrnl.exe` 中 KeSemaphore 相关导出符号；本修复先消除本地竞争。

## 11. 状态

- Fixed

## 12. 修复说明

`acquire()` 和 `release()` 已改为 CAS 循环，成功提交才返回；失败时使用返回的观察值继续重试或判定已到边界。宿主单元测试和 x86-64 构建均通过。
