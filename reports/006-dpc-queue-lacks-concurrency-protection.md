# 问题 #6：每 CPU DPC 队列缺少并发保护

## 1. 问题编号

`6`

## 2. 问题位置

- 文件路径：`src/ke/dpc.zig`
- 函数/模块：`queueDpc()`、`drainAtDispatchLevel()`、`DpcFifo`
- 行号或代码片段：两个函数直接读取和修改 `q.head`、`q.tail`、`q.count` 与 `q.fifo`，队列操作周围没有锁或中断屏蔽。

## 3. 问题描述

同一 CPU 槽上的 DPC FIFO 可以在多个执行上下文中被访问。若排队操作与排空操作并发发生，环形队列的头部、尾部和计数更新可能交错，导致丢项、重复执行、队列指针错乱或越界访问。

## 4. 复现路径

当某 CPU 正在 `drainAtDispatchLevel()` 中读取或弹出 DPC 项时，若同一 CPU 的中断或其他上下文调用 `queueDpc()`，两次执行都会更新同一个 `DpcFifo`。该问题通常需要压力测试或竞争窗口命中才能复现。

## 5. 影响范围

- 影响所有使用通用 DPC 的驱动和内核延迟工作。
- 可能导致输入刷新等 DPC 回调丢失、重复执行或队列状态损坏。
- 损坏的队列指针可能进一步造成内核内存访问异常或数据竞争。

## 6. 严重程度

- High

## 7. 可能原因

DPC 模块按 CPU 划分队列，减少了跨处理器竞争，但没有处理同一 CPU 上中断上下文与普通上下文的抢占。缺少中断屏蔽或自旋锁意味着环形队列操作不是原子的。

## 8. 权威参考依据

- 项目源码：`src/ke/dpc.zig` 的队列实现与调用点。
- 项目源码：`src/ke/spinlock.zig` 提供可保存并恢复中断状态的 IRQ 自旋锁。
- WDK 公开描述 DPC 在 DISPATCH_LEVEL 运行，但本报告的竞争窗口来自项目实现审计；未引用 REA 对 Windows 7 镜像的二进制分析结论。
- `/home/mobtgzhang/api.json` 是 REA 接入配置，不是 Windows API 行为文档。

## 9. 建议修复方案

为每个 CPU 槽增加独立的 IRQ 自旋锁，保护队列元数据和 `input_flush_pending` 的读写。执行回调前应释放队列锁，避免回调内再次排队时造成递归持锁；回调执行期间的新排队请求可在回调结束后继续排空。

## 10. 验证方法

- 运行内核构建与现有输入、DPC 或中断相关测试。
- 在 QEMU 中触发键盘/鼠标中断和高频定时器负载，观察 DPC 回调是否稳定执行且无队列异常。
- 后续可用 REA 对照 `ntoskrnl.exe` 或 HAL 中 DPC 排队路径的实际同步行为；本报告当前不声称已进行该二进制对照。

## 11. 状态

- Fixed

## 12. 修复说明

为每个 `DpcFifo` 增加独立 `IrqSpinLock`，保护 `head`、`tail`、`count` 和 `input_flush_pending`。`queueDpc()` 与输入刷新请求在锁内更新队列；`drainAtDispatchLevel()` 在执行回调前释放队列锁，回调结束后重新获取锁继续排空，避免回调内排队导致递归持锁。构建和 config/boot 回归测试通过；中断压力下的 QEMU 长时运行仍需后续验证。
