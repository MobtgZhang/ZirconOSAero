# 问题 #14：堆 `prev` 合并在非链头节点后仍截断空闲链表

## 1. 问题编号

`14`

## 2. 问题位置

- 文件路径：`src/mm/heap.zig`
- 函数/模块：`insertFreeBlock()`
- 行号或代码片段：`prev` 合并分支中 `pr.next = block.next;` 后原修复又执行 `if (block.next == null) free_head = prev;`。

## 3. 问题描述

问题 #10 的修复为了处理“合并结果成为链尾”的情况，把 `free_head` 回写为 `prev`。但只有 `prev` 是原链头时这个回写才正确。若空闲链表中存在更早的节点，例如 `first -> middle -> tail`，插入块与 `tail` 合并且合并结果成为链尾，回写会把链头改为 `middle`，导致 `first` 以及其前缀从空闲链表中永久丢失。

## 4. 复现路径

1. 构造三条非相邻空闲块链 `first -> middle -> tail`。
2. 在 `middle` 与 `tail` 之间插入一个与 `tail` 相邻、与 `middle` 不相邻的块。
3. 插入块先与 `tail` 合并为新的链尾，再进入 `prev` 合并分支。
4. 原修复会把 `free_head` 写成 `middle`，`first` 丢失。

可在同文件单元测试中直接构造该链表状态并调用 `insertFreeBlock()` 复现。

## 5. 影响范围

- 堆前缀空闲区间被永久丢失，造成可用内存减少和虚假 OOM。
- 空闲链表与实际可回收内存不一致，影响 `heap_check()` 与调试统计的可信度。
- 长期运行的内核池、驱动缓冲、文件系统和对象路径可能受影响。

## 6. 严重程度

- Critical

## 7. 可能原因

#10 的修复把“合并块是链尾”和“合并块前驱是链头”混为同一条件。实际上，`prev` 合并后只要 `prev` 已存在，链头就不需要改变；`free_head` 只在 `prev == null` 时需要指向新合并块，而这个赋值早已由按地址插入路径完成。

## 8. 权威参考依据

- 项目源码：`src/mm/heap.zig` 的 `insertFreeBlock()`、`freeListDebug()`、`heap_check()` 与现有合并测试。
- 操作系统教科书中按地址排序的空闲链表合并不变量；该问题是实现内部链表不变量错误，不依赖 Windows 7 专有内部布局。
- `/home/mobtgzhang/api.json` 是 REA 接入配置，不是堆内部实现文档；本报告未从中提取语义。

## 9. 建议修复方案

删除 `prev` 合并分支中对 `free_head` 的额外回写。保留按地址插入时的链头更新；`prev` 已存在时，链头自然保持不变，合并后的前驱节点继续作为链表节点。

## 10. 验证方法

- 新增测试构造 `first -> middle -> tail`，插入与 `tail` 相邻的块，断言 `free_head` 仍为 `first` 且合并结果为 128 字节链尾。
- 运行 `zig build test`，并保留现有三块连续释放的回归测试。
- 运行 `zig build -Darch=x86_64` 确认内核构建不回归。
